## 0. Executive Summary (Краткий вывод)

**todo-md не относится к классу SDD-инструментов** в классическом понимании. Он решает другую задачу: управление задачами (task management) через файловую систему и git, а не спецификация поведения системы (specification of system behavior).

**Ключевые различия:**
- SDD-инструменты специфицируют **ЧТО делает система** (OpenSpec: `specs/` как source of truth); todo-md специфицирует **ЧТО нужно сделать** (задача с метаданными).
- **Куда записывается результат планирования:** SDD → спецификация поведения системы (`specs/`); todo-md → задача/эпик (`todo/`).
- SDD-инструменты формализуют **поведение системы** (требования, сценарии: `Requirement:`, `Scenario:`); todo-md формализует **постановку задачи** (типизированные поля front matter, фреймворки User Story/Job Story, SMART, MoSCoW, DoD, валидатор структуры).

**Однако** todo-md пересекается с SDD по **принципу работы с артефактами**: и `specs/` (SDD), и `todo/` (todo-md) — это структурированные машино-читаемые файлы, которые одновременно:
1. служат **договорённостью для людей** (читаются и согласовываются);
2. дают **контекст ИИ-агенту** (шаблоны, справочники, AGENTS.md);
3. являются **основой для автоматизации** (CLI, валидатор, доска).

Различие — в **содержании артефакта** (поведение системы vs постановка задачи), а не в принципе.

**Позиционирование:** todo-md — это легковесный, портативный набор правил для управления задачами (создание, статусы, канбан) и контекстом для ИИ-агентов. SDD-инструменты нужны, когда требуется **спецификация поведения системы** и машино-проверяемое соответствие кода ей. Оба дают трассируемость: todo-md — изменений (задача↔ветка↔PR↔коммиты, статусы, даты, git-история), SDD — требований (спецификация↔код). Разница в формате и цели артефактов, а не в наличии интеграции с AI.

## 1. Что такое SDD (Specification-Driven Development)

### Определение

**SDD (Specification-Driven Development)** — подход к разработке, при котором система описывается через спецификации (specs), являющиеся «источником правды» (source of truth). Суть: сначала согласовать спецификации, затем дизайн, задачи и реализацию.

### Признаки SDD

1. **Спецификации как source of truth** — описание текущего поведения системы (`specs/`) отдельно от предлагаемых изменений (`changes/`).
2. **Формализованный формат** — структурированные требования, сценарии, домены (OpenSpec: `Requirement:`, `Scenario:`).
3. **Workflow через спецификации** — proposal → specs → design → tasks → implement.
4. **Интеграция с AI** — агенты создают/валидируют спецификации, следуют им при написании кода.
5. **Архитектурная дисциплина** — машинно-проверяемое соответствие кода спецификации (requirement traceability), compliance-аудит.

### Задачи, которые решает SDD

- Согласование требований между стейкхолдерами.
- Предотвращение расхождения кода и документации.
- Управление сложными изменениями, затрагивающими подсистемы.
- Контроль архитектурных ограничений и зависимостей.
- Трассируемость изменений от требования до реализации.

## 3. Обзор инструментов

### 3.1 OpenSpec

**Суть:** Лёгкий «слой соглашений» между человеком и ИИ-ассистентом.

**Формат спецификаций:**
- `openspec/specs/<domain>/spec.md` — текущее поведение с требованиями и сценариями
- `openspec/changes/<change-name>/` — предложенные изменения (proposal, specs, design, tasks)
- Префиксы: `Requirement:` и `Scenario:` для автоматизации

**Workflow:**
```
Draft Change Proposal → Review & Align (edit specs/tasks) → Implement Tasks (AI writes code) → Archive & Update Specs
```

**Роль AI:**
- Агенты создают артефакты по шаблонам (например, `/opsx:ff` генерирует все планировочные файлы)
- Люди задают интент и ограничения, агенты превращают в краткие, проверяемые спецификации
- AI следует инструкции `apply`: читает контекст, работает по задачам, помечает готовые

**Команды:**
- `/opsx:explore` — для неясных требований (сравнение опций, ASCII-диаграммы, риски)
- `/opsx:verify` — проверка соответствия реализации дымчатым спекам
- `/opsx:archive` — завершение изменений с архивацией знаний

**Область применения:**
- Команды, где планирование предшествует коду
- Работа пересекает границы репозиториев

**Сильные стороны:**
- Лёгкость (соглашения, не фреймворк)
- Спецификации как source of truth
- Поддержка команд через stores
- Наглядные ASCII-диаграммы, сравнение опций

**Слабые стороны (вывод из контекста):**
- Нет явных механизмов контроля качества (кроме verify)
- Требует дисциплины команды следовать workflow

**Целевой размер команды/проекта:**
- Малые и средние команды, где важна формализация, но энтерпрайз-функционал избыточен

### 3.2 BMAD

**Суть:** Модульная экосистема для установки навыков (skills), агентов и вспомогательных ресурсов через манифест-спецификацию.

**Формат спецификации:**
- JSON-манифест `.claude-plugin/plugin.json`
- Обязательные поля: `name`, `version`, `description`, `bmad.specVersion`, `bmad.code`, `bmad.compatibility.bmadMethod` (semver-диапазон, например `>=6.6.0 <7.0.0`)
- Опциональные поля: `skills`, `agents`, `commands`, `hooks`, `mcpServers`, `license`, `homepage`, `keywords`, `author`, `displayName`
- Все ресурсы лежат в обычных директориях (например, `./skills/...`, `./agents/...`)

**Валидация:**
- Скрипт `scripts/validate-module.mjs` проверяет обязательные поля, корректность `name`, semver-версии, пути к ресурсам, резервированные `bmad.code`
- Валидатор проверяет коллизии имён с официальными скиллами (предупреждение W03)

**Роль AI:**
- Модули могут содержать скиллы (SKILL.md с frontmatter) и агентов Claude
- Официальные BMAD-агенты (например, `bmad-agent-architect`, `bmad-agent-dev`, `bmad-agent-pm`) выполняют роли планировщика, разработчика, PM и т.д.
- BMAD используется как хост для планирования и разработки (SDD-подход)

**Область применения:**
- Организация разработки через спецификации
- Элиситация требований
- Создание PRD, дизайн-документов, историй разработки
- Ревью кода

**Сильные стороны:**
- Формализованный манифест с валидацией
- Модульность — расширяемость через плагины
- Интеграция с Claude Code

**Слабые стороны (вывод из контекста):**
- Привязка к Claude Code
- Экосистема может быть сложной для понимания новичками

**Целевой размер команды/проекта:**
- Разработчики, использующие Claude Code и желающие расширять его модулями

### 3.3 sdd (z-hua/sdd)

**Суть:** Плагин для Claude Code, объединяющий OpenSpec (WHAT) и Superpowers (HOW) в единый workflow с жёсткими качественными требованиями.

**Workflow:**
```
Isolate → Specify → Brainstorm → Plan → Execute (Subagents + TDD) → Verify → Finish + Archive
```

**Формат спецификаций:**
- Используется OpenSpec формат: proposal, delta-спеки, архивация
- Команды: `/opsx:propose`, `/opsx:verify`, `/opsx:archive`

**Роль AI:**
- Агенты-субагенты выполняют фазы (изоляция, спецификация, мозговой штурм, планирование, исполнение с TDD, верификация, архивация)
- AI следует Iron Laws (спецификации перед кодом, тесты перед реализацией, root cause перед фиксом, доказательства перед утверждениями, архивация знаний)
- Subagent-driven development с двухэтапным ревью

**Область применения:**
- Сложные изменения, охватывающие несколько подсистем
- Проекты, где требуется жёсткий контроль качества

**Сильные стороны:**
- Интегрирует OpenSpec и Superpowers
- Жёсткий workflow с TDD и двухэтапным ревью
- Обязательная изоляция через worktree
- «Specs are the source of truth» — при расхождении кода со спекой сначала обновляется спецификация
- Verify включает полный тест-сьют и evidence-based проверку

**Слабые стороны (вывод из контекста):**
- Привязка к Claude Code, OpenSpec, Superpowers
- Высокая порог входа (требует понимания всех компонентов)
- Жёсткий workflow может быть избыточным для простых задач

**Целевой размер команды/проекта:**
- Сложные изменения, затрагивающие несколько подсистем
- Команды, которые могут позволить себе сложный setup

### 3.4 Helix

**Суть:** AI-native платформа для программной инженерии (не просто фреймворк для агентов), организующая управляемую и проверяемую разработку через спецификации, архитектурные правила и детерминированные пайплайны.

**Устройство:**
- 3 уровня: Governance (что разрешено), Knowledge (что нужно знать), Execution (выполнение работ)
- Зависимости строго направлены: `apps → application → engine contracts → core`
- Пайплайн: Workspace → Manifest Loader → Specification Registry → Context Resolver → Execution Planner → Provider Adapter → Review/Quality Gates → Repository Change/PR
- Основные движки: Core, Governance, Knowledge, Repository, Execution, Plugin

**Формат спецификаций:**
- Спеки в OpenSpec-формате с доменами (например, `core-primitives`, `conflict-impact-atlas`) и сценариями (WHEN…THEN)
- Архитектурные решения фиксируются в ADR (например, ADR-0004 про техстек)

**Архитектурные правила:**
- Нет циклических зависимостей
- Core не зависит от инфраструктуры/Node.js — адаптеры подключаются через контракты
- Плагины не зависят друг от друга
- Публичные API — через корни пакетов
- Оркестрация детерминирована и тестируема
- Конституция (H-CON): секреты не в коде, никаких скрытых допущений (H-CON-011), провайдер-независимость (H-CON-012), поддерживаемость людьми и агентами (H-CON-013)

**Роль AI:**
- AI — «исполнительные агенты» с чёткими миссиями (например, Specification Author создаёт точные, тестируемые спеки; запрещено скрывать неоднозначности)
- Используется для управляемой эволюции кодовой базы: предложение изменений → спецификация → планирование → выполнение → ревью → PR

**Область применения:**
- Энтерпрайз-разработка
- Проекты с требованиями к compliance-аудиту и трассируемости требований (соответствие кода спецификации)

**Сильные стороны:**
- Строгая архитектурная дисциплина (машинно-проверяемые правила)
- Трассируемость и аудит
- Независимость от конкретного AI-провайдера
- Детерминированное выполнение

**Слабые стороны (вывод из контекста):**
- Высокая начальная стоимость (манифесты, ADR, конституция)
- Риск излишней формализации для маленьких проектов
- Жёсткие правила могут замедлить эксперименты

**Целевой размер команды/проекта:**
- Энтерпрайз-проекты с требованиями к аудиту и архитектурному контролю

### 3.6 GitHub Spec Kit (официальный)

**Суть:** Официальный инструментарий GitHub для SDD — specify CLI + slash commands + 3 модели персистентности.

**Формат спецификаций:**
- Структура проекта: `.specify/` (конституция) + `specs/NNN-feature-name/` (spec.md, plan.md, tasks.md)
- spec.md — требования и user stories (ЧТО и ПОЧЕМУ)
- plan.md — технический план (КАК, tech stack, архитектура)
- tasks.md — список задач для реализации

**Workflow (slash commands):**
```
/speckit.constitution → /speckit.specify → /speckit.plan → /speckit.tasks → /speckit.implement → /speckit.converge
```
- `/speckit.constitution` — принципы проекта
- `/speckit.specify` — что хотим построить (требования)
- `/speckit.plan` — технический подход (tech stack)
- `/speckit.tasks` — список задач
- `/speckit.implement` — выполнить задачи
- `/speckit.converge` — сравнить код со спекой/планом/задачами, добавить недостающие задачи

**3 модели персистентности спек:**

| Модель | Правило мутации | Spec остаётся source of truth? |
|--------|-----------------|-------------------------------|
| **Flow-back** | Любой артефакт (spec, plan, tasks, code) может быть изменён, потом reconcile | ⚠️ Частично — spec.md остаётся «trustworthy» |
| **Flow-forward** | Новые требования → новая папка фичи, старые immutable | ✅ Да |
| **Living** | spec.md — контракт, plan/tasks regenerated | ✅ Да |

**Ключевое отличие от «code as spec»:**
- Flow-back допускает изменения в коде, которые влияют на спеку
- НО: «Do not leave a lower-level change in code if spec.md still says something different and the spec is meant to remain trustworthy»
- Спецификации хранятся ОТДЕЛЬНО от кода (`specs/` директория)

**Связь спецификаций и кода:**
- `/speckit.converge` — «Assess the codebase against spec/plan/tasks and append remaining work as new tasks»
- Спецификации проверяют код на соответствие, не заменяют его

**Роль AI:**
- Генерирует spec.md, plan.md, tasks.md по командам
- Исполняет задачи через `/speckit.implement`
- Работает с 30+ AI coding agents (Copilot, Claude, и др.)

**Область применения:**
- Любые проекты (greenfield, brownfield, creative exploration)
- Команды, которые хотят структурированного SDD-процесса
- Мульти-технологичные проекты

**Сильные стороны:**
- 3 модели персистентности — выбор под стиль команды
- 30+ интеграций с AI-агентами
- Конституция проекта для принципов
- Flow-back допускает гибкость (код может влиять на спеку)

**Слабые стороны (вывод из контекста):**
- SpecKit-спецификации хранятся отдельно от кода (не «code as spec»)
- Требует установки specify CLI (uv tool)
- Flow-back требует дисциплины (не оставлять расхождение код/спека)

**Целевой размер команды/проекта:**
- Любой размер — flow-back для быстрых итераций, living/flow-forward для формальных процессов

**Примечание:** источники проанализированы через прямое чтение документации GitHub (TasK processing).

### 3.7 spec-kit (plaesy)

**Суть:** Система для создания технических спецификаций и архитектурных документов с готовыми шаблонами.

**Формат спецификаций:**
- Шаблоны: `sdd.template.md` (Software Design Description), `icd.template.md` (Interface Control Document), `fsd.template.md` (Functional Specification Document)
- SDD-шаблон основан на **IEEE 1016-2017**: введение, цели/ограничения, архитектурный обзор, виды (4+1), дизайн компонентов, данных, интерфейсов, обоснование решений, качественные атрибуты, риски
- Структура папок: `requirements/`, `design/`, `specifications/`, `plan/architecture/`, `plan/implementation/`, `tasks/.../implements/`

**Связь спецификаций и кода:**
- «Implementation Complete When: All code files implemented per specs» — код реализуется по спецификациям
- Спецификации — отдельные артефакты от кода
- Задачи (`tasks/{tasks-id}/implements/`) содержат логи разработки, ссылаются на спецификации

**Роль AI:**
- Не явно описан (spec-kit — в первую очередь шаблоны и структура)
- Спецификации могут быть использованы AI для генерации кода

**Область применения:**
- Команды, которым нужны формализованные спецификации по стандарту IEEE
- Проекты с требованиями к документации

**Сильные стороны:**
- Готовые шаблоны по стандарту IEEE 1016-2017
- Структурированная организация артефактов
- Чек-листы готовности по фазам (research → clarification → implementation → review)

**Слабые стороны (вывод из контекста):**
- Требует дисциплины следовать структуре
- Возможная избыточность документации для небольших проектов

**Целевой размер команды/проекта:**
- Средние и крупные команды с требованиями к формальной документации

### 3.8 superspec

**Суть:** Расширение для spec-kit, объединяющее SDD с возможностями агента superpowers.

**Формат спецификаций:**
- Структура проекта: `.specify/` (конституция, шаблоны) и `specs/NNN-feature-name/` (spec.md, plan.md, tasks.md, progress.yml, checklist)
- Использует шаблоны spec-kit

**Workflow (6 фаз):**
```
Constitution → Specify → Brainstorm → Plan → Tasks → Execute → Review
```
- Каждая фаза имеет явный гейт и человеческие чекпоинты
- `progress.yml` отслеживает фазы для возобновляемости сессий

**Связь спецификаций и кода:**
- `/speckit.superspec.execute` — «Orchestrate implementation with TDD + subagents»
- `/speckit.superspec.review` — «Run code review against spec requirements»
- Код проверяется «against spec requirements»

**Роль AI:**
- Интеграция с superpowers (мозговой штурм, планирование, TDD, субагенты, код-ревью)
- Агенты следуют спецификациям при написании кода

**Область применения:**
- Команды, использующие spec-kit и желающие интеграции с AI-агентами
- Сложные проекты с многофазным workflow

**Сильные стороны:**
- Объединяет spec-kit и superpowers
- 6-фазный workflow с гейтами
- Возобновляемость сессий через `progress.yml`

**Слабые стороны (вывод из контекста):**
- Сложный setup (spec-kit + superpowers + superspec)
- Привязка к экосистеме superpowers

**Целевой размер команды/проекта:**
- Команды, уже использующие spec-kit или superpowers
- Сложные проекты с многоэтапной разработкой

### 3.9 hybrid-spec-framework

**Суть:** Обучающая методология для создания исполняемых спецификаций через быстрый прототип и обратную инженерию.

**Подход (гибридный):**
```
Build minimal prototype → Extract specifications → Validate with multiple AIs
```
- На начальном этапе допускается быстрый прототип (код)
- Итоговая цель — отдельные исполняемые спецификации
- Спецификации валидируются несколькими ИИ-моделями

**Формат спецификаций:**
- 4 спецификационных документа на выходе
- Структурированы одновременно для людей и для ИИ
- Требования: «Precise acceptance criteria, Unambiguous constraints, Machine-parseable formats»

**Связь спецификаций и кода:**
- Код — промежуточный шаг для извлечения знаний
- «Reverse (code→specs)» в отличие от Spec Kit — «Forward (specs→code)»
- Все модели реализуют проект по спецификациям, а не по коду

**Роль AI:**
- Извлечение спецификаций из кода (reverse engineering)
- Кросс-модельная валидация спецификаций
- Реализация по спецификациям (multiple AIs)

**Область применения:**
- Обучение команд SDD-подходам
- Проекты, где уже есть код/прототип, но нет спецификаций

**Сильные стороны:**
- Практичный подход (начать с прототипа, а не с чистого листа)
- Кросс-модельная валидация повышает качество
- «Reusable blueprint that ANY AI can execute»

**Слабые стороны (вывод из контекста):**
- Требует нескольких ИИ-моделей для валидации
- Двухэтапный процесс (прототип → спеки → реализация)

**Целевой размер команды/проекта:**
- Команды, обучающиеся SDD
- Проекты с существующим кодом, но без спецификаций

## 4. todo-md — краткое описание

**Суть:** Канбан для управления задачами через markdown-файлы с YAML front matter.

**Формат хранения:**
- `.md`-файлы с YAML front matter
- Поля: `type`, `status`, `priority`, `complexity`, `value`, `cost_plan`, `cost_fact`, `depends_on`, `epic`, `author`, `assignee`, `branch`, `pr`
- Структура папок: `todo/` (активные), `todo/backlog/`, `todo/done/`, `todo/cancelled/`

**Workflow задач:**
```bash
start  TASK-foo   # → in_progress (проставляет started)
review TASK-foo   # → review
done   TASK-foo   # → done, перенос в done/ (проставляет completed)
cancel TASK-foo   # → cancelled, перенос в cancelled/
backlog TASK-foo  # → backlog, перенос в backlog/
set    TASK-foo priority=P1  # точечная правка метаданных
```

**Валидация:**
- Проверяет YAML front matter, обязательные поля, допустимые значения
- Проверяет соответствие ID в имени файла и заголовке
- Проверяет локальные Markdown-ссылки (чинит при переходах статусов)
- Проверяет соответствие статуса папке

**Дашборд:**
- Канбан с колонками по статусам
- Группировка по эпикам
- Графики (тепловая карта, распределения, гистограмма, scatter)
- Диаграмма Ганта

**Связь с кодом:**
- Опциональные поля `branch`, `pr` в front matter для отслеживания изменений

**Роль AI:**
- Шаблоны (`task.md`, `epic.md`) дают структуру задачи
- Справочники (типы, статусы, приоритеты, сложность) дают контекст
- AGENTS_TASK_WRITING_GUIDE.md даёт правила постановки
- AI-агент получает это как контекст и следует формату

**Зависимости:**
- PHP 8.4
- Без внешних библиотек

**Зрелость:**
- Альфа

## 6. В чём сходство todo-md с SDD-инструментами

1. **Формальная структура** — YAML front matter задаёт унифицированные поля, позволяет автоматизировать валидацию, CLI, доску.
2. **Контекст для AI** — шаблоны и справочники дают AI-агенту правила постановки и формат задачи.
3. **Workflow через команды** — CLI-команды задают атомарные переходы между статусами.
4. **Архивация знаний** — папки `done/`, `cancelled/` хранят завершённые задачи.

**НО:** ключевое различие в том, ЧТО специфицируется и КАК код относится к спецификациям.

## 7. В чём отличие todo-md от SDD-инструментов

### 7.1 Поддержка «code as spec»

| Инструмент | Поддерживает «code as spec»? | Отношение к коду |
|------------|------------------------------|------------------|
| OpenSpec | ❌ | Specs are source of truth, code — implementation |
| BMAD | ❌ | Манифест описывает модули, не поведение системы |
| sdd | ❌ | «Specs before code — No implementation without a specification first» |
| Helix | ❌ | Спецификации содержат требования, код реализует их |
| spec-kit | ❌ | «All code files implemented per specs» |
| superspec | ❌ | Code checked «against spec requirements» |
| hybrid-spec-framework | ❌ | Код — материал для извлечения спек, не замена |
| **todo-md** | **✅** | **Код = спецификация текущего состояния, задачи = изменения** |

**Ключевой вывод:** todo-md — единственный из проанализированных 8 инструментов, который поддерживает модель «code as spec». Все SDD-инструменты следуют паттерну **«specs before code»** — спецификации обязательны и являются источником правды.

### 7.2 Другие различия

1. **Цель спецификации:**
   - SDD-инструменты: описывают поведение системы (ЧТО делает система)
   - todo-md: описывают изменения (ЧТО изменить в коде)

2. **Направление работы:**
   - SDD-инструменты (forward): спецификации → дизайн → задачи → код
   - todo-md: код (текущее состояние) → задача (план изменения) → код (новое состояние)

3. **Верификация:**
   - SDD: проверяет соответствие кода спецификации (verify, TDD)
   - todo-md: валидирует структуру задачи, но не код

4. **Формализация:**
   - SDD: специфицируют **поведение системы** — формализованные требования/сценарии (`Requirement:`, `Scenario:`, IEEE 1016-2017)
   - todo-md: специфицирует **постановку задачи** — типизированные поля front matter (enum: V0–V4, C0–C5, P0–P3), фреймворки User Story/Job Story, SMART, MoSCoW, DoD; валидатор проверяет структуру

## 8. Вывод: относится ли todo-md к SDD?

**Прямой ответ:** todo-md не относится к классу SDD-инструментов в их текущем понимании.

**Обоснование:**

### 8.1 Все SDD-инструменты следуют паттерну «specs before code»

Из 7 проанализированных инструментов (OpenSpec, BMAD, sdd, helix, spec-kit, superspec, hybrid-spec-framework):
- **0 инструментов** поддерживают модель «code as spec»
- **Все 8 инструментов** требуют отдельные спецификации
- **Общий паттерн:** спецификации — источник правды, код — реализация

### 8.2 todo-md следует другому паттерну

```
SDD-инструменты:      specs (источник правды) → design → tasks → code → verify
todo-md:              code (текущее состояние) → задача (изменение) → code (новое состояние)
```

**todo-md = Change-Driven Development, а не Specification-Driven Development**

### 8.3 todo-md соответствует 1 из 5 признаков SDD

| Признак SDD | OpenSpec | spec-kit | sdd | helix | superspec | hybrid | todo-md |
|-------------|----------|----------|-----|-------|-----------|--------|---------|
| Спецификации поведения системы | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| Отдельный слой спецификаций | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| «Specs before code» | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| Интеграция с AI при написании кода | ✅ | частично | ✅ | ✅ | ✅ | ✅ | ❌ (контекст) |
| Архитектурная дисциплина | ❌ | частично | ❌ | ✅ | ❌ | ❌ | ❌ |

### 8.4 Классификация

**todo-md — это:**
- ✅ **File-based task tracker** с формализованным форматом
- ✅ **Change-SDD** — спецификация ИЗМЕНЕНИЙ (не поведения системы)
- ✅ **Code-as-Spec** — код = спецификация текущего состояния

**todo-md — это НЕ:**
- ❌ **System-SDD** — нет спецификации поведения системы
- ❌ **Классический SDD-инструмент** — не следует «specs before code»

### 8.5 Возможная классификация SDD

```
Specification-Driven Development
├── System-SDD (классический)
│   ├── OpenSpec — markdown-спеки поведения системы
│   ├── spec-kit — SDD по IEEE 1016-2017
│   ├── superspec — 6-фазный workflow
│   ├── sdd — OpenSpec + Superpowers
│   ├── helix — энтерпрайз-платформа
│   └── hybrid-spec-framework — обратная инженерия
└── Change-SDD (альтернативный)
    └── todo-md — задачи как спецификации изменений кода
```

**Или более точно:**
```
SDD = разработка, управляемая спецификациями (в любой форме)
  - System Specification (поведение системы) — OpenSpec, spec-kit, ...
  - Implementation Specification (состояние кода) — todo-md (code as spec)
  - Change Specification (план изменений) — todo-md (задачи)
```

### 8.6 Финальный ответ

**Если использовать классическое определение SDD (как у OpenSpec/sdd/spec-kit):**
→ todo-md **не относится** к SDD-инструментам

**Если использовать широкое определение SDD (любые спецификации, включая code as spec):**
→ todo-md относится к SDD как **Change-SDD** или **Implementation-SDD**

**Рекомендация:** использовать термин **Change-SDD** для todo-md, чтобы отличать от классического System-SDD.

## 9. Позиционирование: когда выбрать что

### Выбрать todo-md, если:
- Нужен легковесный таск-трекер без базы данных
- Команда использует git и markdown
- Достаточно простых задач с метаданными
- Не требуется спецификация поведения системы
- Не нужен строгий архитектурный контроль
- Команда: solo → малые (до 5 человек)

### Выбрать OpenSpec, если:
- Нужны спецификации как source of truth
- Требуется workflow через спецификации (propose → specs → design → tasks → implement)
- Команда хочет agreement layer между людьми и AI
- Проект пересекает границы репозиториев
- Команда: малые → средние

### Выбрать BMAD, если:
- Используется Claude Code
- Нужна модульная экосистема для расширения
- Требуется формализованный манифест с валидацией
- Команда: разработчики Claude Code

### Выбрать sdd (z-hua/sdd), если:
- Нужен жёсткий workflow с TDD и двухэтапным ревью
- Изменения сложные, затрагивают несколько подсистем
- Используются Claude Code + OpenSpec + Superpowers
- Команда: любые, для сложных изменений

### Выбрать Helix, если:
- Энтерпрайз-проект с требованиями к compliance-аудиту и трассируемости требований
- Нужна строгая архитектурная дисциплина
- Требуется независимость от AI-провайдера
- Команда: энтерпрайз

## 15. Обсуждение: альтернативные определения SDD

### 15.1 Почему никто не поддерживает «code as spec»?

Все 7 проанализированных SDD-инструментов следуют паттерну **«specs before code»**. Возможные причины:

1. **Спецификации для людей и AI** — код труден для чтения людьми, спецификации более декларативны.
2. **Отделение намерения от реализации** — спецификация описывает ЧТО и ПОЧЕМУ, код — КАК.
3. **Верифицируемость** — проще проверить код на соответствие спецификации, чем понять код как спецификацию.
4. **Трассируемость** — отдельные спецификации дают явную трассировку от требования до реализации.
5. **Мульти-модельная реализация** — одна спецификация → несколько AI-моделей для реализации.

### 15.2 Преимущества «code as spec» (todo-md подход)

1. **Упрощение** — не нужно синхронизировать спеки и код.
2. **Актуальность** — код всегда актуален (спеки могут устаревать).
3. **Портативность** — работает везде, где есть файлы и git.
4. **Низкий порог входа** — не нужно учить форматы спецификаций.

### 15.3 Недостатки «code as spec»

1. **Код не описывает намерение** — только реализацию, не «почему».
2. **Трудность верификации** — сложно понять, соответствует ли код требованиям.
3. **Нет трассируемости требований** — чистый «code as spec» не связывает требование с кодом. todo-md частично закрывает это через трассируемость изменений (задача↔ветка↔PR↔коммиты, статусы, даты, git-история), но не даёт машино-проверяемого соответствия «код ↔ спецификация поведения».
4. **Проблемы для AI** — код императивен, не декларативен.

### 15.4 Возможные гибридные подходы для todo-md

```
code-as-spec + external-specs:

src/                    ← спецификация текущего состояния (код)
docs/specs/             ← внешние спецификации поведения системы (опционально)
todo/
  ├── TASK-*.md         ← спецификация изменения (ссылка на spec и код)
  └── EPIC-*.md         ← группа изменений (ссылка на spec)
```

**Возможные доработки:**
- Добавить поле `spec_ref` для ссылки на внешнюю спецификацию
- Добавить секцию «Спецификация» с WHEN/THEN сценариями
- Добавить команду `derive` для создания задач из спецификаций
- Добавить поддержку ADR для архитектурных решений

### 15.5 Заключение

**SDD — это не монолитный подход, а спектр:**

```
Жёсткий SDD (OpenSpec/sdd) ←→ Гибридный (hybrid-spec) ←→ Code-as-Spec (todo-md)
```

**Выбор подхода зависит от:**
- Размера команды и проекта
- Требований к compliance-аудиту и трассируемости требований
- Готовности инвестировать в спецификации
- Баланса между формализацией и скоростью

**todo-md занимает нишу:**
- Solo и малые команды
- Проекты без строгих требований к аудиту
- Быстрая разработка с минимальной формализацией
- Git-first подход
