# Сводный анализ: идеи для агентов и людей в todo-md

Дата: 2026-07-25.

Отбор из трёх сравнений (`mdtask`, `kanban-md`, `taskwarrior`) по двум критериям — польза агентам и польза людям — с оглядкой на то, чем проект является сейчас.

## Главный вывод

Для **агентов** файл-first + стандартный shell (`ls`, `find`, `grep`, `awk`, `cat`) — родной интерфейс, и он сильнее самописного CLI на стороне чтения. Агенты владеют shell как базовым знанием: он не стоит контекста, а конвейерные цепочки (`|`, `xargs`) мощнее любой команды, которую мы напишем. Поэтому **read-side CLI (`list`/`show`/индекс) для агентов не нужен** — `grep` строит любой обзор по demand и всегда свежий.

Это не убивает CLI целиком, а сужает: shell силён в **чтении**, но слаб в **атомарных безопасных записях** (переход состояния + перенос файла + правка ссылок). Там CLI всё ещё может быть не избыточен.

## Контекст, который нельзя игнорировать

- Идентичность (`AGENTS.md`): строгий Markdown-стандарт постановки задач для AI-разработки, документация на первом месте, **минимум зависимостей — только PHP 8.4**, init обратно совместим.
- В самом пакете: 2 скрипта (`init`, `validate`), документация, шаблоны, справочники; собственный `todo/` почти пуст. Мерить масштаб по нему нельзя.
- Реальный масштаб (per-project, подсчёт 2026-07-25): **TasK** — ~430 задач/эпиков (38 эпиков, 25 активных, 110 в бэклоге, 289 выполнено); **stocks2** — 156; **task-orchestrator** — 164. Масштаб мерится внутри одного проекта, а не суммой по потребителям.
- Распределение (`composer.json`): `bin: [init, validate]` — любой новый скрипт автоматически уходит всем потребителям через `vendor/bin/`.

## Файл-first + shell против CLI (для агентов)

Аргумент, который пересмотрел анализ:

- `ls todo/`, `grep -H "^status: review" todo/*.todo.md`, `find todo -name 'TASK-chat-*.todo.md'`, `awk` над выводом — агенты делают это из коробки, без контекста и без обучения.
- Самописный `todo-md list --status=review` требует, чтобы агент знал команду, флаги и формат вывода — всё это грузится в контекст. А PHP-CLI не догонит `grep`/`rg` ни в скорости, ни в гибкости конвейера.
- Канбан-папки (`todo/`, `backlog/`, `done/`, `cancelled/`) уже дают и агенту, и человеку «доску» через `ls`.
- Генерируемый индекс (`INDEX.md`) — **не лучше**: `grep` уже даёт свежий обзор по demand, а индекс лишь добавляет риск устаревания и ту же болезнь «доверия артефакту».

Где CLI всё ещё может быть не избыточен:

- **Изменение состояния** (`done`/`create`/`set`) — атомарная запись: `status` + перенос в папку + правка ссылок + проверка. Shell делает это плохо (см. №2). Это не read-side, поэтому файл-first критика чтения его не касается.
- Производные запросы (готова/заблокирована, с раскрытыми зависимостями) — объединения по многим файлам; `grep` делает их плохо. Но это отложенные идеи (отчёты).
- Не-LLM потребитель `--json` (CI, панель мониторинга) — если такой появится. Пока не подтверждён.

## Где это бьёт по прежним выводам

- Прежнее «масштаб склоняет к Варианту В (стать инструментом)» — неверно для агентов. Масштаб закрывается shell на стороне чтения. Развилка разрешается в пользу файл-first.
- Прежнее «`list` окупается масштабом» и «генерируемый индекс — №2» — отвергнуты файл-first логикой: `grep`/`awk` делают это свежее и без генератора.

## Где я осторожнее источников

- **`--json` может быть преждевременным.** Фиксировать схему, пока формат ещё меняется (поля стоимости добавили только что), — рискованное обязательство по совместимости.
- **Read-side CLI и индекс для агентов избыточны** против shell. Источники этого не учитывают: они экстраполируют из не-file-first продуктов.
- **Инструкции для агентов (skills) переоценены** для двойного критерия: людям почти не полезны.

## Где я согласен с источниками

- **Тесты** — не «нужность 10/10 сейчас»; это фундамент для mutating-операций. Достаточно лёгких контрольных примеров.
- **Захват задач, TUI, срочность, метрики, пользовательские поля** — рано или противоречит сути.
- **Блок результата** — мелочь, полезна обеим сторонам.

## Топ-3

### №1. Усилить валидатор: проверка существования `depends_on`/`epic` + починить ссылку AGENTS

**Идея.** В существующем `todo-md-validate` собрать индекс ID всех `.todo.md` и проверять, что `depends_on` и `epic` ведут на существующие задачи и эпики. Заодно — одна правка: битая ссылка на несуществующий `docs/todo-md/AGENTS.md` (07-04 P0.1).

**За.**

- Полезно обеим аудиториям: агентам — ловля их собственных битых ссылок (которые `grep` прошёл бы молча), людям — ловля опечаток.
- Полностью в рамках проекта: усиливает ядро, ничего не добавляет потребителю.
- Дёшево: валидатор уже разбирает front matter, нужна только перекрёстная проверка.
- 07-04 уже ставит это в P0.

**Против.**

- Ложные срабатывания на исторических и отменённых зависимостях. Решение: ссылка на `cancelled` — предупреждение, а не ошибка.
- Самозависимости и циклы пока не ловим — на потом.

**Почему №1.** Сильна по всем осям: обеим аудиториям, в рамках проекта, дёшево. Не требует решения о судьбе проекта. Делать первым.

### №2. Изменение состояния (`create`/`done`/`set`) — атомарная безопасная запись

**Идея.** `todo-md done <ID>` (и `start`/`review`/`cancel`/`backlog`), `create`, `set`. Каждая атомарно: правит `status`, переносит файл в нужную папку, чинит относительные ссылки, прогоняет валидатор и отказывается сохранять при ошибке.

**За.**

- Это **не запрос, а запись** — поэтому файл-first критика чтения её не касается. Shell (`grep`/`ls`) силён в чтении, но не в атомарных переходах состояния с правкой ссылок.
- Доказательство — эта же сессия: я перенёс задачу в `done/` **корня репозитория** вместо `todo/done/`. `mv`+`sed` не знают канонического пути и не чинят относительные ссылки в эпиках/соседях. CLI знал бы.
- Обеим аудиториям: агенту — не развалить доску, человеку — одна команда вместо правки front matter + переноса + починки ссылок + `validate`.

**Против.**

- Самая опасная категория: mutating-операции над файлами пользователя. Нужны fixture-тесты, проверка коллизий, позже — undo. Без тестов выпускать нельзя.
- Высокая стоимость и это всё же CLI — может не пройти ваш файл-first барьер: агент способен и `mv`+`sed`+`validate`, а мой перенос был ошибкой дисциплины, не обязательно повод для нового инструмента.
- Тянет за собой вопрос undo/починки — дополнительный объём.

**Вердикт.** Единственный CLI-угол, у которого оправдание не бьётся файл-first критикой: shell сильнее в чтении, но не в атомарных записях с правкой ссылок. Но стоимость высока, и решение за владельцем — считать ли мой ошибочный перенос достаточным поводом, или хватит дисциплины `mv`+`sed`+`validate`. Безусловных read-side CLI-идей для агентов больше нет.

### №3. Блок результата `Implemented:` + правило «документация актуальна при смене поведения»

**Идея.** В шаблон задачи — короткий блок результата, заполняемый при завершении. Правило: задача, меняющая поведение, обновляет README и документацию в том же PR.

**За.**

- Обеим аудиториям: агентам — понятная передача работы (следующий агент видит, что сделано), людям — сигнал для проверки.
- В рамках проекта: конвенция шаблона и документации, ноль кода.
- Затраты минимальные.

**Против.**

- Маленькая идея, не «прорыв». Слот №3 мал, потому что всё масштабнее либо ломает файл-first суть, либо полезно одной стороне.
- Может стать мёртвой секцией без поддержки в валидаторе.

## Честная оговорка о размере списка

Под файл-first линзой пространство агентских улучшений **тоньше**, чем казалось из трёх сравнений. Read-side полностью закрывается shell (`grep`/`awk`/`ls`), поэтому read-CLI и индекс отвергнуты. Безусловны только №1 (гарантии валидатора — то, чего shell сам себе не даст) и №3 (формат/конвенция). №2 (безопасная запись) — единственный выживший CLI-угол, и то на усмотрение владельца. Это не провал анализа, а вывод: для агентской аудитории todo-md уже близок к оптимуму как файл-first + shell.

## Что я НЕ рекомендую

- Read-side CLI `list`/`show`/`--json` и генерируемый индекс — для агентов избыточны против shell.
- Захват задач, TUI, срочность, метрики, пользовательские поля, обработчики событий, версионирование схемы, файл настроек, теги, повторяющиеся задачи — рано или противоречит сути.

## Вопросы владельцу

1. Считать ли мой ошибочный перенос задачи достаточным поводом для mutating-CLI (№2), или хватит дисциплины `mv`+`sed`+`validate`?
2. Есть ли реальный не-LLM потребитель `--json` (CI/панель мониторинга)? Если нет — read-side CLI не нужен и для людей.
3. Команды ради людей (таблица/сводка) — нужны ли, если канбан-папки + `ls` уже дают доску?
