# Сводный анализ: идеи для агентов и людей в todo-md

Дата: 2026-07-25.

Отбор из трёх сравнений (`mdtask`, `kanban-md`, `taskwarrior`) по двум критериям — польза агентам и польза людям — с оглядкой на то, чем проект является сейчас.

## Главный вывод

Две аудитории — два разных интерфейса:

- **Агентам** файл-first + стандартный shell (`ls`, `find`, `grep`, `awk`, `cat`) — родной интерфейс и сильнее самописного CLI на стороне чтения. Shell не стоит контекста, а конвейеры (`|`, `xargs`) мощнее любой нашей команды. Поэтому **read-side CLI (`list`/`show`/индекс) для агентов не нужен**.
- **Людям** для обзора нужно больше, чем канбан-папки + `ls`: дашборды и диаграммы Ганта. Их даёт **детерминированный генератор** поверх общего парсера — и именно здесь `--json`/структурированный экспорт зарабатывает своё место (как контракт данных, не как агентская команда).

CLI выживает в двух местах: (а) атомарные безопасные записи — №2; (б) данные для генератора человеческих отчётов — №3.

## Контекст, который нельзя игнорировать

- Идентичность (`AGENTS.md`): строгий Markdown-стандарт постановки задач для AI-разработки, документация на первом месте, **минимум зависимостей — только PHP 8.4**, init обратно совместим.
- В самом пакете: 2 скрипта (`init`, `validate`), документация, шаблоны, справочники; собственный `todo/` почти пуст. Мерить масштаб по нему нельзя.
- Реальный масштаб (per-project, подсчёт 2026-07-25): **TasK** — ~430 задач/эпиков (38 эпиков, 25 активных, 110 в бэклоге, 289 выполнено); **stocks2** — 156; **task-orchestrator** — 164. Масштаб мерится внутри одного проекта, а не суммой по потребителям.
- Распределение (`composer.json`): `bin: [init, validate]` — любой новый скрипт автоматически уходит всем потребителям через `vendor/bin/`.

## Файл-first + shell против CLI (для агентов)

- `ls todo/`, `grep -H "^status: review" todo/*.todo.md`, `find todo -name 'TASK-chat-*.todo.md'`, `awk` над выводом — агенты делают это из коробки, без контекста и без обучения.
- Самописный `todo-md list --status=review` требует, чтобы агент знал команду, флаги и формат вывода — всё это грузится в контекст. А PHP-CLI не догонит `grep`/`rg` ни в скорости, ни в гибкости конвейера.
- Канбан-папки (`todo/`, `backlog/`, `done/`, `cancelled/`) уже дают и агенту, и человеку минимальную «доску» через `ls`.
- Генерируемый индекс (`INDEX.md`) — не лучше: `grep` уже даёт свежий обзор по demand, а индекс лишь добавляет риск устаревания и ту же болезнь «доверия артефакту».

Вывод: read-side CLI для агентов **не делать**. CLI оправдан только там, где shell объективно слаб — атомарная запись (№2) и данные для генератора отчётов (№3).

## Где я осторожнее источников

- **`--json` оправдан, но контракт фиксировать рано.** Потребитель есть (генератор отчётов), но фиксировать стабильную JSON-схему, пока формат задач ещё меняется (поля стоимости добавили только что), — рискованно. Сначала стабилизировать формат и завести версионирование контракта.
- **Read-side CLI и индекс для агентов избыточны** против shell. Источники этого не учитывают: они экстраполируют из не-file-first продуктов.
- **Инструкции для агентов (skills) переоценены** для двойного критерия: людям почти не полезны.

## Где я согласен с источниками

- **Тесты** — не «нужность 10/10 сейчас»; это фундамент для mutating-операций. Достаточно лёгких контрольных примеров.
- **Захват задач, TUI, срочность, метрики, пользовательские поля** — рано или противоречит сути (часть закроет генератор отчётов).
- **Блок результата** — мелочь, полезна обеим сторонам.

### За пределами проекта

Захват задач, TUI, теги, пользовательские поля, срочность, метрики, обработчики событий, отмена/починка, облегчённый шаблон для C0/C1, SQLite/облачная синхронизация, числовые ID, полный язык запросов Taskwarrior — рано или противоречит сути. Детали — в 07-04.

**Зависимость для Ганта:** временная диаграмма Ганта требует lifecycle-дат (`due`/`started`/`completed`), которых в схеме пока нет (только `created`). Дашборд (статусы/приоритеты/эпики/прогресс) строится сейчас; Гант по времени — после добавления дат (это повышает приоритет lifecycle-дат).

## Топ-3

### №1. Усилить валидатор: проверка существования `depends_on`/`epic` + починить ссылку AGENTS

**Идея.** В существующем `todo-md-validate` собрать индекс ID всех `.todo.md` и проверять, что `depends_on` и `epic` ведут на существующие задачи и эпики. Заодно — одна правка: битая ссылка на несуществующий `docs/todo-md/AGENTS.md` (07-04 P0.1). Этот же парсер/индекс — фундамент для №3.

**За.**

- Полезно обеим аудиториям: агентам — ловля их битых ссылок (которые `grep` прошёл бы молча), людям — ловля опечаток.
- Полностью в рамках проекта: усиливает ядро, ничего не добавляет потребителю.
- Дёшево и переиспользуемо: парсер/индекс работает и в валидаторе, и в генераторе отчётов (№3).
- 07-04 уже ставит это в P0.

**Против.**

- Ложные срабатывания на исторических и отменённых зависимостях. Решение: ссылка на `cancelled` — предупреждение, а не ошибка.
- Самозависимости и циклы пока не ловим — на потом.

**Почему №1.** Сильна по всем осям: обеим аудиториям, в рамках проекта, дёшево, и кладёт фундамент (парсер) для №3. Делать первым.

### №2. Изменение состояния (`create`/`done`/`set`) — атомарная безопасная запись

**Идея.** `todo-md done <ID>` (и `start`/`review`/`cancel`/`backlog`), `create`, `set`. Каждая атомарно: правит `status`, переносит файл в нужную папку, чинит относительные ссылки, прогоняет валидатор и отказывается сохранять при ошибке.

**За.**

- Это **запись, не запрос** — файл-first критика чтения её не касается. Shell (`grep`/`ls`) силён в чтении, но не в атомарных переходах состояния с правкой ссылок.
- Доказательство — эта же сессия: я перенёс задачу в `done/` **корня репозитория** вместо `todo/done/`. `mv`+`sed` не знают канонического пути и не чинят относительные ссылки в эпиках/соседях. CLI знал бы.
- Обеим аудиториям: агенту — не развалить доску, человеку — одна команда вместо правки front matter + переноса + починки ссылок + `validate`.

**Против.**

- Самая опасная категория: mutating-операции над файлами пользователя. Нужны fixture-тесты, проверка коллизий, позже — undo. Без тестов выпускать нельзя.
- Тянет за собой вопрос undo/починки — дополнительный объём.

**Вердикт.** Единственный CLI-угол на стороне записи, оправдание которого не бьётся файл-first критикой. Владелец согласен (2026-07-25): агенту тяжело держать в голове все детали перехода — status, папку, ссылки, валидацию, — скриптом проще. Берём; обязательное условие — fixture-тесты до выпуска.

### №3. Генератор дашбордов и диаграмм Ганта (HTML) для людей

**Идея.** Детерминированный инструмент: по `.todo.md` (через общий парсер из №1) генерирует HTML — дашборд (статус-карта, распределение по приоритетам/эпикам/исполнителям, прогресс) и диаграмму Ганта. `--json`/структурированный экспорт — контракт между парсером и генератором.

**За.**

- Закрывает человеческую сторону двойного критерия: обзор, который канбан-папки + `ls` не дают (агрегаты, диаграммы, зависимости).
- Детерминированная генерация: файлы → HTML, воспроизводимо, без ручной правки.
- Переиспользует парсер из №1 — не новый фундамент.
- Направление согласовано владельцем (2026-07-25).

**Против.**

- Prospective, следующая фаза — не немедленно.
- Нужен стабильный `--json`/формат-контракт — а формат ещё меняется. Сначала версионировать.
- **Гант по времени требует lifecycle-дат** (`due`/`started`/`completed`), которых в схеме нет. Дашборд — сейчас; Гант — после добавления дат (либо структурный «Гант» по эпикам/`depends_on` без оси времени).

**Вердикт.** Главный человеческий выигрыш и смысл реабилитации `--json`. Делать после №1 (парсер) и стабилизации формата; для Ганта — сначала добавить lifecycle-даты.

## Честная оговорка о размере списка

Под файл-first линзой место для агентских улучшений узкое: read-side закрывается shell, поэтому read-CLI и индекс отвергнуты. Безусловны №1 (валидатор/парсер) и №2 (безопасная запись, согласован). Для людей добавляется содержательная №3 (генератор отчётов) — она и оправдывает `--json`. Так двойной критерий закрывается: агентам — файл-first + shell + валидатор + mutating-CLI, людям — то же для работы + генератор дашбордов/Ганта для обзора.

## Что я НЕ рекомендую

- Read-side CLI `list`/`show` и генерируемый индекс — для агентов избыточны против shell.
- Захват задач, TUI, пользовательские поля, обработчики событий, версионирование схемы, файл настроек, теги, повторяющиеся задачи — рано или противоречит сути.

## Решённые вопросы (2026-07-25)

1. **Потребитель `--json`?** Да, перспективный — генератор дашбордов/Ганта для людей. Это реабилитирует `--json` (как слой данных, не агентскую команду); контракт фиксировать после стабилизации формата.
2. **Нужно ли людям больше, чем папки + `ls`?** Да — дашборды/Гант (см. №3).
