# Сводный анализ: идеи для агентов и людей в todo-md

Дата: 2026-07-25.

Отбор из трёх сравнений (`mdtask`, `kanban-md`, `taskwarrior`) по двум критериям — польза агентам и польза людям — с оглядкой на то, чем проект является сейчас.

## Главный вывод

Для **агентов** файл-first + стандартный shell (`ls`, `find`, `grep`, `cat`) — родной интерфейс, и он сильнее самописного CLI. Агенты владеют shell как базовым знанием: он не стоит контекста, а конвейерные цепочки (`|`, `xargs`) мощнее любой команды, которую мы напишем. Поэтому направление улучшений для агентов — **усиливать файл-first формат и его гарантии, а не строить CLI-слой**, дублирующий `grep` хуже него самого.

Это заставило пересмотреть мою прежнюю рекомендацию: я переоценивал read-only CLI (`list`/`show`/`--json`), думая, что агентам нужен «машиночитаемый API». Агентам и так родной текст файлов — им нужен надёжный, предсказуемый формат, а не ещё одна команда.

## Контекст, который нельзя игнорировать

- Идентичность (`AGENTS.md`): строгий Markdown-стандарт постановки задач для AI-разработки, документация на первом месте, **минимум зависимостей — только PHP 8.4**, init обратно совместим.
- В самом пакете: 2 скрипта (`init`, `validate`), документация, шаблоны, справочники; собственный `todo/` почти пуст. Мерить масштаб по нему нельзя.
- Реальный масштаб (per-project, подсчёт 2026-07-25): **TasK** — ~430 задач/эпиков (38 эпиков, 25 активных, 110 в бэклоге, 289 выполнено); **stocks2** — 156; **task-orchestrator** — 164. Масштаб мерится внутри одного проекта, а не суммой по потребителям.
- Распределение (`composer.json`): `bin: [init, validate]` — любой новый скрипт автоматически уходит всем потребителям через `vendor/bin/`.

## Файл-first + shell против CLI (для агентов)

Аргумент, который перевернул №2:

- `ls todo/`, `ls todo/backlog/`, `grep "^status: review" todo/*.todo.md`, `find todo -name 'TASK-chat-*.todo.md'` — агенты делают это из коробки, без контекста и без обучения.
- Самописный `todo-md list --status=review` требует, чтобы агент знал команду, её флаги и формат вывода — всё это грузится из `AGENTS.md`/инструкций в контекст. А PHP-CLI не догонит `grep`/`rg` ни в скорости, ни в гибкости конвейера (`|`, `xargs`, `wc`).
- Канбан-папки (`todo/`, `backlog/`, `done/`, `cancelled/`) уже дают и агенту, и человеку «доску» через обычный `ls`.

Где CLI всё ещё может быть не избыточен (узкие случаи):

- Производные запросы: «готова» (без блокеров), «заблокирована», с раскрытыми зависимостями — это объединения по многим файлам, `grep` их делает плохо. Но это именно отложенные идеи (отчёты), а не базовый `list`/`show`.
- Не-LLM потребитель `--json` (CI, панель мониторинга) — если такой появится. Пока не подтверждён.

Вывод: базовый CLI `list`/`show` для агентов **не делать**. CLI оправдан только под подтверждённую потребность людей (таблица) или внешнего JSON-потребителя — и позже.

## Где это бьёт по прежним выводам

- Прежнее «масштаб склоняет к Варианту В (стать инструментом)» — неверно для агентов. Масштаб показывает потребность управлять многими задачами, но для агентов она закрывается shell, а не CLI. Развилка разрешается в пользу файл-first.
- Прежнее «`list` окупается масштабом» — относилось к людям, не к агентам. Для агентов `list` избыточен против `grep` при любом масштабе.

## Где я осторожнее источников

- **`--json` может быть преждевременным.** Фиксировать схему, пока формат ещё меняется (поля стоимости добавили только что), — рискованное обязательство по совместимости.
- **CLI для агентов избыточен против shell** (см. выше). Источники этого не учитывают: они экстраполируют из не-file-first продуктов.
- **Инструкции для агентов (skills) переоценены** для двойного критерия: людям почти не полезны.

## Где я согласен с источниками

- **Тесты** — не «нужность 10/10 сейчас»; это фундамент для mutating-операций. Достаточно лёгких контрольных примеров.
- **Захват задач, TUI, срочность, метрики, пользовательские поля** — рано или противоречит сути.
- **Блок результата** — мелочь, полезна обеим сторонам.

## Топ-3

### №1. Усилить валидатор: проверка существования `depends_on`/`epic` + починить ссылку AGENTS

**Идея.** В существующем `todo-md-validate` собрать индекс ID всех `.todo.md` и проверять, что `depends_on` и `epic` ведут на существующие задачи и эпики. Заодно — одна правка: битая ссылка на несуществующий `docs/todo-md/AGENTS.md` (07-04 P0.1).

**За.**

- Полезно обеим аудиториям: агентам — ловля их собственных битых ссылок (которые `grep` прошёл бы молча), людям — ловля опечаток.
- Полностью в рамках проекта: усиливает ядро, ничего не добавляет потребителю.
- Дёшево: валидатор уже разбирает front matter, нужна только перекрёстная проверка по индексу.
- 07-04 уже ставит это в P0.

**Против.**

- Ложные срабатывания на исторических и отменённых зависимостях. Решение: ссылка на `cancelled` — предупреждение, а не ошибка.
- Самозависимости и циклы пока не ловим — на потом.

**Почему №1.** Сильна по всем осям сразу: обеим аудиториям, в рамках проекта, дёшево. Не требует решения о судьбе проекта. Делать первым.

### №2. Генерируемый индекс доски (`todo/INDEX.md`)

**Идея.** Один markdown-файл-сводка: ID, статус, приоритет, эпик, заголовок — таблицей по всем задачам. Агент читает доску одним файлом вместо обхода сотен; генерируется утилитой или git-хуком.

**За.**

- Родное для агента: усиливает файл-first, не конкурирует с `grep` (это не команда, а файл). На вопрос «что в `todo/`» отвечает одним чтением — именно то, с чего началась эта сессия.
- Помогает и людям: быстрый обзор без открытия десятков файлов.
- Снижает расход контекста агента: одна читалка вместо N.

**Против.**

- Регенерация при изменениях: нужна дисциплина, git-хук или шаг в CI; иначе индекс врёт и хуже, чем отсутствие.
- Дубль источника правды: данные те же, что в файлах; риск рассинхрона.

**Почему №2 и почему опционально.** Это единственная содержательная файл-first идея поверх №1. Но если владелец считает, что агенту хватает `grep` (см. принцип выше), — индекс не нужен. Решение за владельцем; это не безусловная рекомендация.

### №3. Блок результата `Implemented:` + правило «документация актуальна при смене поведения»

**Идея.** В шаблон задачи — короткий блок результата, заполняемый при завершении. Правило: задача, меняющая поведение, обновляет README и документацию в том же PR.

**За.**

- Обеим аудиториям: агентам — понятная передача работы (следующий агент видит, что сделано), людям — сигнал для проверки.
- В рамках проекта: конвенция шаблона и документации, ноль кода.
- Затраты минимальные.

**Против.**

- Маленькая идея, не «прорыв». Слот №3 мал, потому что всё масштабнее либо ломает файл-first суть, либо полезно одной стороне.
- Может стать мёртвой секцией без поддержки в валидаторе.

## Честная оговорка о размере списка

Под файл-first линзой пространство агентских улучшений **тоньше**, чем казалось из трёх сравнений. №1 (валидатор) и №3 (блок результата) — безусловные; №2 (индекс) — на усмотрение. CLI-слой для агентов отпадает. Это не провал анализа, а вывод: для агентской аудитории todo-md уже близок к оптимуму как файл-first + shell, и работа — это гарантии и формат, а не операционный CLI.

## Что я НЕ рекомендую

- Базовый CLI `list`/`show`/`--json` **для агентов** — избыточен против shell.
- Захват задач, TUI, срочность, метрики, пользовательские поля, обработчики событий, версионирование схемы, файл настроек, теги, повторяющиеся задачи — рано или противоречит сути.

## Вопросы владельцу

1. Нужен ли генерируемый индекс доски (№2), или агенту достаточно `grep`?
2. Есть ли реальный не-LLM потребитель `--json` (CI/панель мониторинга)? Если нет — CLI-`--json` не нужен.
3. CLI ради людей (таблица/сводка) — нужен ли, если канбан-папки + `ls` уже дают доску?
4. Команды изменения состояния (`create`/`done`/`set`) — делать ли, если проект осознанно остаётся стандартом, а не инструментом?
