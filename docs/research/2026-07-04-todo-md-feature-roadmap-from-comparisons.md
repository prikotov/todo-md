# Аудированный список фич для развития todo-md

Дата: 2026-07-04.

Основа: перепроверка текущего репозитория `todo-md` и ранее подготовленных сравнений:

- [`mdtask-comparison.md`](./mdtask-comparison.md)
- [`kanban-md-comparison.md`](./kanban-md-comparison.md)
- [`taskwarrior-comparison.md`](./taskwarrior-comparison.md)

Цель: убрать завышения и фантазии из roadmap. Оценки ниже относятся к текущему `todo-md` как к PHP-пакету с документацией, init-скриптом и валидатором, а не к гипотетическому полноценному task manager.

## Что фактически уже есть в todo-md

Проверено по `README.md`, `composer.json`, `.github/workflows/ci.yml`, `bin/todo-md-init`, `bin/todo-md-validate`, `docs/todo-md/`, `todo/`.

- Есть Composer-пакет `prikotov/todo-md` для PHP 8.4.
- Есть bin-скрипты:
  - `todo-md-init` — создаёт `todo/`, `todo/backlog/`, `todo/done/`, `todo/cancelled/`, копирует `docs/todo-md/`, копирует `todo/AGENTS.md`, обновляет `.gitignore`.
  - `todo-md-validate` — валидирует `.todo.md` задачи и эпики.
- Есть документация:
  - руководство постановки задач;
  - справочники типов, статусов, приоритетов, сложности, ценности, стоимости, AI-агентов;
  - шаблоны `task.md` и `epic.md`.
- Есть строгая модель task/epic:
  - `TASK-*.todo.md`, `EPIC-*.todo.md`;
  - YAML front matter;
  - Human Brief;
  - SMART / User Story / Job Story / MoSCoW;
  - `type`, `created`, `value`, `complexity`, `priority`, `author`, `assignee`, `status`;
  - `depends_on`, `epic`, `branch`, `pr` для задач;
  - `cost_plan`, `cost_fact` как optional integer-поля.
- Валидатор уже проверяет:
  - наличие front matter;
  - обязательные поля;
  - допустимые значения enum-полей;
  - формат `created`;
  - формат `cost_plan` / `cost_fact`;
  - ID в имени файла и H1;
  - обязательные секции;
  - локальные Markdown-ссылки;
  - соответствие папки и `status` для `backlog`, `done`, `cancelled`;
  - template placeholders и незаполненные `- [ ] ...` / `- ...`.
- CI уже запускает:
  - `composer validate --strict`;
  - `php -l bin/todo-md-init`;
  - `php -l bin/todo-md-validate`;
  - `php bin/todo-md-validate .`.
- Нет `tests/` и fixture-регрессий.
- Нет единого `todo-md` CLI и команд `list`, `show`, `create`, `move`, `edit`, `note`.
- Нет JSON/compact output.
- Нет config-файла.
- Нет tags, due/started/completed/updated, ready/urgency, claims, hooks, TUI.

## Дополнительные факты, найденные при перепроверке

- В `AGENTS.md` есть ссылка на `docs/todo-md/AGENTS.md`, но такого файла в проекте нет. Реальный source для consumer rules сейчас — `todo/AGENTS.md`, который копирует init-скрипт.
- `.idea/` уже находится в `.gitignore` и не отслеживается Git.
- `tmp/` сейчас не отслеживается Git. В `.gitignore` отдельного правила для `tmp/` нет.
- `docs/research/**` уже содержит tracked-файлы исследований.
- `todo/TASK-*.todo.md` уже содержит tracked внутреннюю задачу развития пакета.
- Значит реальный вопрос поставки через Composer касается только tracked-файлов, которые мы сами держим в репозитории: `docs/research/**` и `todo/TASK-*.todo.md`.

## Шкала оценок

- **Качество сейчас** — насколько фича уже реализована в текущем `todo-md`: `1` нет реализации, `10` хорошо реализовано.
- **Нужность сейчас** — важность для текущего docs-first пакета: `1` можно не делать, `10` критично.
- **Уверенность** — насколько вывод подтверждён кодом и документацией проекта: `1` предположение, `10` прямой факт.
- **Мнение владельца** — поле для решения владельца проекта: брать / не брать / отложить / изменить формулировку.
- **Сделано** — чекбокс выполнения: `[ ]` не сделано, `[x]` сделано.

## Исправленный приоритет

Ниже — рабочая доска решений. В поле **Мнение владельца** можно писать: `берём`, `не берём`, `отложить`, `изменить`, `нужна задача`, `обсудить`, свободный комментарий.

Формат каждого предложения:

- **Проблема** — что именно сейчас не так.
- **Конкретика** — какие файлы, команды или сценарии затрагиваются.
- **Предлагаемое решение** — что именно изменить.
- **Проверка** — как убедиться, что изменение работает.
- **Мнение владельца** — поле для решения.

Важно: новый CLI не является самоцелью. Текущие `todo-md-init` и `todo-md-validate` уже закрывают базовые операции пакета. Команды `list/show/create/move/edit/board` стоит брать только при подтверждённой боли: много задач, частые ошибки ручного редактирования, необходимость машинного обзора для AI-агентов или CI.

### P0 — реальные ближайшие задачи

#### P0.1. Исправить несоответствие ссылок на AGENTS

- **Проблема:** в `AGENTS.md` есть ссылка на `docs/todo-md/AGENTS.md`, но такого файла в проекте нет. Фактический файл правил для потребителя — `todo/AGENTS.md`.
- **Конкретика:**
  - есть файл: `todo/AGENTS.md`;
  - нет файла: `docs/todo-md/AGENTS.md`;
  - спорная ссылка: `AGENTS.md` → раздел «Ссылки»;
  - init-скрипт копирует `todo/AGENTS.md` в consumer project как `todo/AGENTS.md`.
- **Предлагаемое решение:**
  - выбрать один источник истины;
  - минимальный вариант: заменить ссылку в корневом `AGENTS.md` с `docs/todo-md/AGENTS.md` на `todo/AGENTS.md`;
  - альтернативный вариант: добавить `docs/todo-md/AGENTS.md` и изменить init-скрипт так, чтобы он не дублировал/не конфликтовал с `todo/AGENTS.md`.
- **Проверка:**
  ```bash
  grep -R "docs/todo-md/AGENTS.md" -n AGENTS.md README.md docs todo || true
  php bin/todo-md-init /tmp/todo-md-init-check
  ```

#### P0.2. Усилить валидатор связей `depends_on` и `epic`

- **Проблема:** валидатор проверяет формат `depends_on` и `epic`, но не проверяет, что указанные задачи и эпики реально существуют. Из-за этого можно получить валидную задачу с несуществующей зависимостью.
- **Конкретика:**
  - затронут файл: `bin/todo-md-validate`;
  - текущая проверка `depends_on`: plain ID формата `TASK-*` или `EPIC-*`;
  - текущая проверка `epic`: plain ID формата `EPIC-*`;
  - не проверяется существование файла в `todo/`, `todo/backlog/`, `todo/done/`, `todo/cancelled/`.
- **Предлагаемое решение:**
  - построить индекс ID всех найденных `.todo.md` файлов в рамках одного запуска валидатора;
  - для каждого `depends_on` проверять наличие ID в индексе;
  - для `epic` проверять наличие `EPIC-*` в индексе;
  - не включать self-dependency в первый шаг: кейс редкий и не выглядит критичным;
  - позже, если понадобится, добавить self-dependency как warning или отдельную строгую проверку;
  - warning, а не error, для зависимости на `cancelled` задачу — это может быть исторически допустимо.
- **Проверка:**
  ```bash
  php bin/todo-md-validate .
  ```
  Добавить fixtures:
  - задача с `depends_on: TASK-no-such-task` должна падать;
  - задача с `epic: EPIC-no-such-epic` должна падать.
- **Сделано:** [ ]

#### P0.3. Добавить минимальные fixture-регрессии для существующих CLI

- **Проблема:** CI проверяет синтаксис и валидирует один текущий валидный task-файл. Нет проверки негативных сценариев валидатора и поведения init-скрипта.
- **Конкретика:**
  - уже проверяется:
    - `composer validate --strict`;
    - `php -l bin/todo-md-init`;
    - `php -l bin/todo-md-validate`;
    - `php bin/todo-md-validate .`;
  - не проверяется:
    - что `todo-md-init` создаёт нужные папки;
    - что повторный `todo-md-init` idempotent;
    - что `--force` перезаписывает файлы;
    - что валидатор ловит битую Markdown-ссылку;
    - что валидатор ловит неправильный статус папки;
    - что валидатор ловит placeholders.
- **Предлагаемое решение:**
  - на первом шаге не добавлять PHPUnit: текущий объём PHP-кода можно проверить self-contained CLI-fixtures;
  - добавить shell/PHP checks в `tests/fixtures/` или `tests/cli/`;
  - добавить composer script `test` или отдельную CI-команду `php tests/run.php`;
  - вернуться к PHPUnit позже, если появится общий PHP-код для парсинга/индексации задач, JSON-контракта или mutating CLI-команд `create/move/edit`;
  - держать fixtures маленькими, чтобы проект не превращался в тяжёлую test suite раньше времени.
- **Проверка:**

### P1 — условные CLI-улучшения, только если ручного workflow станет мало

#### P1.1. Условно добавить `todo-md list`

- **Проблема:** сейчас человек или агент должен вручную читать папку `todo/` и открывать файлы, чтобы понять текущие задачи.
- **Конкретика:**
  - источники данных уже есть в front matter:
    - `status` — состояние задачи: `todo`, `review`, `done` и т.д.;
    - `type` — тип задачи из `docs/todo-md/reference/TYPES.md`: `fix`, `feat`, `docs`, `refactor` и т.д.; сейчас это поле важнее для валидации и единообразия, чем для фильтрации;
    - `epic` — plain ID эпика, например `EPIC-release-v1`, если задача относится к эпику;
    - `priority`, `value`, `complexity`, `assignee`, `created` — остальные поля сортировки/обзора;
  - в текущем проекте сейчас один task и нет `EPIC-*.todo.md`, но поле `epic` уже есть в формате задачи и фильтр по нему логичен для задач, связанных с эпиками;
  - фильтр по `type` слабо обоснован для ближайшего шага: тип задачи не отвечает на главный вопрос «что брать в работу следующим»;
  - команда должна быть read-only и не менять файлы;
  - команда должна работать от корня проекта и от папки `todo/`.
- **Предлагаемое решение:**
  - добавлять команду только если ручного просмотра файлов станет недостаточно;
  - если добавляем, начать с минимального обзора без сложного query language;
  - базовые фильтры-кандидаты: `--status`, `--priority`, `--assignee`, `--epic`;
  - не добавлять `--type` в первый вариант: пока нет подтверждённого сценария, где он нужен;
  - фильтр `--type` добавить позже только при реальной боли, например если нужно быстро отделять `docs`/`test`/`fix` задачи в большом backlog;
  - минимальные колонки должны содержать в том числе поля, по которым фильтруем: ID, status, priority, assignee, epic, title.
- **Проверка после реализации:**
  ```bash
  php bin/todo-md list
  php bin/todo-md list --status=review
  php bin/todo-md list --priority=P2
  ```

- **Конкретика:**

## Что точно не делать сейчас

- Не строить полноценный аналог Taskwarrior.
- Не добавлять claims/pick до появления реального multi-agent conflict.
- Не добавлять hooks до mutating CLI.
- Не добавлять tags без сценария фильтрации, который не закрывается `type` / `epic` / `priority`.
- Не делать TUI до стабильного read-only CLI.
- Не считать отсутствие большой test suite проблемой само по себе: текущий проект в основном документный, а существующий код уже smoke-проверяется CI.

## Главный вывод после перепроверки

`todo-md` сейчас — не недоделанный Taskwarrior, а строгий Markdown-стандарт постановки задач с init и validator. Поэтому ближайшие улучшения должны укреплять текущую модель: валидатор, согласованность документации, лёгкие regression fixtures. Тяжёлые workflow-фичи из `kanban-md` и Taskwarrior стоит брать только после появления реальной потребности в полноценном CLI-task-manager, если такой продуктовый поворот вообще нужен.
