# План релиза v0.1.0

## Метаданные

- Тег релиза: `v0.1.0`.
- Тип повышения: `minor` (новая совместимая функциональность).
- База подготовки: `master`, коммит `fb2b1315404d90c1036bbb653749d5f01a5d2a6a` после PR [#35](https://github.com/prikotov/todo-md/pull/35).
- Ветка подготовки: `task/release-0.1.0`.
- Линия выпуска: `release/0.1`, создаётся после слияния подготовки релиза; линия `0.0` больше не активна.
- Ответственный за одобрение: владелец проекта; публикация — AI-агент после разрешения.
- Плановая дата публикации: 2026-09-19.

## Состав

- [PR #35](https://github.com/prikotov/todo-md/pull/35): участники подготовки задач и эпиков — `consultants`, `reviewer`, `approver`, `informed`.
- [Реализованная задача](../../../todo/done/TASK-participant-metadata.todo.md): чтение списков, проверка, атомарная команда `set`, экспорт JSONL и документация.
- Вне релиза: изменения `task-orchestrator`, назначения по нескольким этапам, полный синтаксис YAML.

## Совместимость и риски

- Новые поля необязательны; существующие задачи проходят проверку без изменений, включая `--strict`.
- При экспорте отсутствующие списки представлены как `[]`, одиночные назначения — как `null`.
- Некорректная структура новых полей останавливает проверку и экспорт с ошибкой.
- Миграции данных и изменения окружения не требуются; окна несовместимости нет.
- Потребителям с ограничением Composer `^0.0` нужно явно разрешить `^0.1`.
- Повторный `init` без `--force` не перезаписывает документы: обновление локальных копий требует осознанного сравнения с новой версией.

## Порядок публикации

1. Проверить и слить отдельный запрос с подготовкой релиза в `master` после успешных проверок и явного разрешения пользователя.
2. Обновить локальную `master`, выполнить `composer install`, `composer validate --strict`, `make check`; дождаться успешной CI (непрерывной интеграции) для коммита слияния.
3. Создать `release/0.1` на этом коммите, без дополнительных правок. Проверить отсутствие чужих изменений и существующего тега `v0.1.0`.
4. Из `release/0.1` создать аннотированный тег `v0.1.0` на проверенном коммите. Отправить ветку и только этот тег от имени GitHub App.
5. Создать GitHub Release (публикацию релиза) по существующему тегу с описанием изменений и совместимости.
6. Проверить доступность версии и установку в изолированный каталог. Основную рабочую копию оставить на `master` с чистым состоянием.

## Проверки

До публикации:

- `composer validate --strict`.
- `make check`: синтаксис PHP, валидация задач и 85 тестов.
- Успешная CI и `git diff --check`.
- Отдельной команды `tests-e2e` в пакете нет; штатные тесты запускают реальные команды в изолированных каталогах.

После публикации:

- Удалённый тег и GitHub Release указывают на проверенный коммит.
- Composer через VCS-репозиторий видит `0.1.0`.
- В изолированной установке `todo-md init` копирует справочник участников, а создание, проверка и экспорт задачи поддерживают новые поля.

## Действия при проблеме

- Опубликованный тег не изменять и не удалять.
- Исправление готовить от `v0.1.0` и выпускать как `v0.1.1` после проверок и согласования.
- Причину и воспроизведение фиксировать в GitHub Issue и задаче в `todo/`; при необходимости согласовать исправление с владельцем проекта.
