# LLM-модели участников (Models)

Модели указываются **в составе участника** — в полях `author`, `assignee`, `reviewer`, `approver`, `consultants`, `informed` задач и эпиков. Отдельного поля `model` в front matter нет.

## Формат участника

```
<роль> (<агент>@<модель>[~<уровень>])
```

- `роль` — функциональная обязанность (`Бэкендер`, `Продакт`); см. [ROLES.md](./ROLES.md).
- `агент` — lowercase-идентификатор инструмента (`pi`, `codex-cli`); см. [AI_AGENTS.md](./AI_AGENTS.md).
- `модель` — опционально; lowercase-идентификатор: `[a-z0-9][a-z0-9.:_~-]*` (двоеточие — ollama-теги, тильда допустима внутри имени).
- `уровень` — опционально, только после модели; lowercase-уровень reasoning/thinking: `off`, `low`, `medium`, `high`, `max`.

Разделители: `@` — агент→модель (не `/`, чтобы не путать с нотацией `provider/model`); `~` — уровень мышления.

## Модель и роли

Модель закреплена **за ролью** — в конфиге проекта хранится профиль роли (провайдер, модель, уровень мышления), например `config/chains.yaml`. Задача фиксирует **срез**: кто и на какой модели реально выполнял работу. Конфиг ролей меняется со временем, а записи участников в done-задаче остаются исторической правдой.

Правила заполнения:

- Указывать модель **рекомендуется** для всех участников; уровень мышления — когда профиль роли его задаёт.
- Источник истины для агента — окружение его харнесса (например, `PI_MODEL` / `PI_PROVIDER` / `PI_REASONING_LEVEL` у pi) или профиль его роли, а не «самоописание» модели: LLM угадывает свою модель недостоверно.
- Запись без модели (`Продакт (pi)`) остаётся валидной — для участников, чья модель не важна или неизвестна.

## Как называть модель

Идентификатор берите из документации провайдера или профиля роли **на момент работы**. Примеры (иллюстративные — модели выходят часто и стареют, не копируйте их слепо):

- `glm-5.3-flash`, `glm-5.3` — Z.AI (GLM)
- `k3.1-pro` — Kimi
- `mimo-v2.6-pro` — Xiaomi MiMo
- `deepseek-flash` — DeepSeek
- `huihui-ai:pi-100k` — локальная модель ollama с тегом

Требования к идентификатору: lowercase, `[a-z0-9][a-z0-9.:_~-]*`; дублирование одного и того же имени в разных написаниях не допускается — иначе аналитика размоется.

## Уровни мышления (Thinking)

Канонические уровни: `off`, `low`, `medium`, `high`, `max`.

- Уровень указывается только вместе с моделью: `Бэкендер (pi@glm-5.3-flash~max)`.
- Соответствует настройке reasoning/thinking профиля роли (например, `--thinking` в chains.yaml или `PI_REASONING_LEVEL`).
- Список можно заменить через конфиг `.todo-md.php` (`thinking_levels`) — см. [CONFIG.md](./CONFIG.md).

Одна модель на разных уровнях мышления — разные конфигурации по стоимости и качеству (`glm-5.3-flash~high` и `glm-5.3-flash~max`), поэтому уровень входит в срез наряду с моделью.

## Валидация

Валидатор `todo-md validate` проверяет модель в составе каждого участника:

- **формат** — всегда: lowercase-идентификатор `[a-z0-9][a-z0-9.:_~-]*`, уровень — lowercase-слово после `~`;
- **уровень мышления** — по умолчанию по каноническому списку (`off/low/medium/high/max`); суффикс `~<слово>` считается уровнем, только если слово известно, иначе — часть имени модели (поэтому тильда внутри имени модели безопасна);
- **список моделей** — только если проект задал `models` в конфиге `.todo-md.php`; без списка модели не проверяются по значениям — модели выходят слишком часто для закрытого списка в пакете.

Нарушения — warning, в режиме `--strict` или `strict: true` — error. См. [CONFIG.md](./CONFIG.md).

## Пример

```yaml
author: Продакт (pi@k3.1-pro~low)              # постановщик на Kimi, low
assignee: Бэкендер (pi@glm-5.3-flash~max)      # исполнитель на GLM Flash, max
reviewer: Ревьюер (pi@huihui-ai:pi-100k~medium) # ревью на локальном ollama, medium
```
