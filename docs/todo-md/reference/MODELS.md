# Список LLM-моделей (Models)

Модели указываются **в составе участника** — в полях `author`, `assignee`, `reviewer`, `approver`, `consultants`, `informed` задач и эпиков. Отдельного поля `model` в front matter нет.

## Формат участника

```
<роль> (<агент>@<модель>[~<уровень>][|<модель>[~<уровень>]]...)
```

- `роль` — функциональная обязанность (`Бэкендер`, `Продакт`); см. [ROLES.md](./ROLES.md).
- `агент` — lowercase-идентификатор инструмента (`pi`, `codex-cli`); см. [AI_AGENTS.md](./AI_AGENTS.md).
- `модель` — lowercase-идентификатор: `[a-z0-9][a-z0-9.:_~-]*` (двоеточие — ollama-теги, тильда допустима внутри имени); обязательна после `@`.
- `уровень` — опционально; lowercase-уровень reasoning/thinking: `off`, `low`, `medium`, `high`, `max`; только после модели.
- `|` — резервные модели после основной; первая модель — основная (primary), остальные — резерв (fallback) по порядку применения.

Разделители зарезервированы: `@` — агент→модель (не `/`, чтобы не путать с `provider/model`); `~` — уровень мышления; `|` — резерв. В идентификаторах моделей эти символы запрещены (`|`) или разбираются семантически (`~`).

**Распознавание уровня — семантическое:** суффикс `~<слово>` считается уровнем, только если слово — известный уровень; иначе весь сегмент трактуется как имя модели (поэтому тильда внутри имени модели безопасна). Если префикс — известная модель, а суффикс — не уровень, суффикс признаётся опечаткой уровня (warning). Единственное неоднозначное имя — модель, заканчивающаяся ровно на `~<известный уровень>`: таких имён следует избегать.

Одна модель на разных уровнях мышления — разные конфигурации по стоимости и качеству (`glm-5.3-flash~high` и `glm-5.3-flash~max`), поэтому уровень входит в срез наряду с моделью.

## Модель и роли

Модель закреплена **за ролью** — в конфиге проекта хранится профиль роли (провайдер, модель, уровень мышления), например `config/chains.yaml`. Задача фиксирует **срез**: кто, на каких моделях и уровнях реально выполнял работу. Конфиг ролей меняется со временем (у роли может появиться резервная модель), а записи участников в done-задаче остаются исторической правдой.

Правила заполнения:

- Указывать модель **рекомендуется** для всех участников — постановщика, исполнителя, ревьювера, консультантов; уровень мышления — вместе с моделью, когда профиль роли его задаёт.
- Резервные модели роли фиксируются после основной через `|` — срез показывает и конфигурацию на случай сбоя основной.
- Источник истины для агента — окружение его харнесса (например, `PI_MODEL` / `PI_PROVIDER` / `PI_REASONING_LEVEL` у pi) или профиль его роли, а не «самоописание» модели: LLM угадывает свою модель недостоверно.
- Запись без модели (`Продакт (pi)`) остаётся валидной — для участников, чья модель не важна или неизвестна.

## Уровни мышления (Thinking)

Канонические уровни: `off`, `low`, `medium`, `high`, `max`.

- Уровень указывается только вместе с моделью: `Бэкендер (pi@glm-5.3-flash~max)`.
- Соответствует настройке reasoning/thinking профиля роли (например, `--thinking` в chains.yaml или `PI_REASONING_LEVEL`).
- Список можно заменить через конфиг `.todo-md.php` (`thinking_levels`) — см. [CONFIG.md](./CONFIG.md).

## Валидация

Валидатор `todo-md validate` проверяет модель и уровень мышления в составе каждого участника:

- формат (lowercase-идентификаторы, модель опциональна, уровень — только после модели);
- вхождение модели в канонический список (см. выше) и уровня в список мышления — нарушение выводится как warning, в режиме `--strict` или `strict: true` — как error;
- запись участника без модели и уровня валидна всегда.

## Пример

```yaml
author: Продакт (pi@k3.1-pro~low)                          # постановщик: Kimi, low
assignee: Бэкендер (pi@glm-5.3-flash~max|k3.1-pro~high)    # исполнитель: GLM Flash max, резерв Kimi high
reviewer: Ревьюер (pi@huihui-ai:pi-100k~medium)             # ревью на локальном ollama, medium
```
