## Постановка задач (Definition of Ready)

Перед началом разработки убедись, что в задаче явно зафиксированы:
- обязательные метаданные в YAML front matter (блок между `---` в начале файла):
  - `type`: категория изменений (см. [TYPES.md](../docs/todo-md/reference/TYPES.md))
  - `value`: бизнес-ценность (см. [VALUES.md](../docs/todo-md/reference/VALUES.md))
  - `complexity`: техническая сложность (см. [COMPLEXITY.md](../docs/todo-md/reference/COMPLEXITY.md))
  - `priority`: очередность выполнения (см. [PRIORITIES.md](../docs/todo-md/reference/PRIORITIES.md))
  - `cost_plan`, `cost_fact`: опциональная стоимость в токенах (см. [COST.md](../docs/todo-md/reference/COST.md))
  - `author`: имя создателя задачи (см. [AI_AGENTS.md](../docs/todo-md/reference/AI_AGENTS.md))
  - `created`: дата/время создания; формат — `YYYY-MM-DD` либо `YYYY-MM-DD HH:MM:SS (unix_ts)`, проставляет CLI
  - `due`, `started`, `completed`, `cancelled`: опциональные метки жизненного цикла (плановый срок, старт в `in_progress`, завершение в `done`, отмена в `cancelled`); тот же формат, проставляет CLI; см. [DATES.md](../docs/todo-md/reference/DATES.md)
  - `branch`: имя рабочей ветки; при создании задачи поле остаётся пустым и заполняется только после фактического создания ветки
  - `status`: текущее состояние (см. [STATUSES.md](../docs/todo-md/reference/STATUSES.md))
- секция **"Простое описание (Human Brief)"**: проблема простыми словами, кому она мешает, поверхностный путь решения или прямое указание, что решение не задано в исходном запросе;
- ожидаемый результат на человеческом языке (что изменится в системе или для пользователя);
- контекст и ограничения (где делаем: application/module, ключевые точки входа, интеграции);
- `scope` и `out of scope` (что делаем и что точно не делаем);
- проверяемые критерии выполнения (что считаем "готово" и как это проверим);
- риски и зависимости (включая миграции, `feature flags`, обновление `docs`).

Если хотя бы один пункт неясен — задачу нужно уточнить или декомпозировать до начала разработки.

### Автоматическая проверка

Перед стартом или передачей задачи другому агенту запусти:

```bash
php vendor/bin/todo-md validate
```

Для проверки конкретной задачи:

```bash
php vendor/bin/todo-md validate todo/TASK-example.todo.md
```

Команды смены состояния (`todo-md done` и др.) обновляют ссылки и валидируют автоматически. При ручном редактировании — обнови ссылки и запусти `php vendor/bin/todo-md validate`.

## Декомпозиция задач

Цель — держать задачу небольшой и однородной, чтобы её можно было быстро проверить.

Правила:
- 1 задача (`<ID>.todo.md`) = 1 логическая подзадача = 1 атомарный набор изменений.
- Декомпозируй задачу, если:
  - затрагиваются несколько независимых частей системы (разные модули, приложения или контексты);
  - для реализации нужен `refactor` или чистка кода (выноси в отдельную задачу);
  - смешиваются механические изменения (`move/rename/format`) и изменения поведения/логики;
  - по факту в процессе работы `diff` быстро разрастается (ориентир — около 600 строк `added + deleted`).

## Структура файла задачи и именование

Каждая задача оформляется в отдельном markdown-файле с именем `<ID>.todo.md`.

### Правила именования ID

ID задачи должен быть уникальным и следовать формату: `TASK-<категория>-<краткое-название>`.
ID эпика следует формату: `EPIC-<категория>-<краткое-название>`.

Примеры:
- `TASK-diarization-perf-optimize`
- `EPIC-code-quality-usecase-naming`

## Процесс работы с задачами

1. **Создание задачи**:
   - `php vendor/bin/todo-md create <ID> --type=<тип> --title="Название"` — создаёт файл из шаблона с валидным front matter, проставляет `created`. Для эпика: `EPIC-<категория>-<название>` (без `--type`).
   - Заполнить секцию **"Простое описание (Human Brief)"** до технических требований.
   - Если задача входит в эпик, передать `--epic=<EPIC-ID>` и обновить план эпика.

2. **Подтверждение задачи (Reverse Briefing)**:
   - Перед стартом (`in_progress`) исполнитель обязан подтвердить понимание.
   - Если "План реализации" заполнен автором: подтвердить, что план ясен.
   - Если "План реализации" пуст: **исполнитель заполняет его самостоятельно**, описывая свое техническое решение. Это гарантирует, что исполнитель видит тот же результат, что и автор.

3. **Выполнение задачи**:
   - `php vendor/bin/todo-md start <ID>` — атомарно переводит `status` в `in_progress`, проставляет `started`.
   - `php vendor/bin/todo-md set <ID> assignee="..."` — заполнить исполнителя.
   - Создать рабочую ветку и заполнить `branch`: `php vendor/bin/todo-md set <ID> branch=task/...`.
   - Обновлять прогресс в критериях выполнения.

4. **Завершение задачи**:
   - Создать Pull Request и заполнить `pr`: `php vendor/bin/todo-md set <ID> pr=https://...`.
   - `php vendor/bin/todo-md review <ID>` — переводит `status` в `review`.
   - После апрува: `php vendor/bin/todo-md done <ID>` — переводит в `done`, переносит файл в `todo/done/`, проставляет `completed`. Относительные ссылки в эпике и соседних задачах обновляются автоматически.

5. **Блокировка**:
   - Если задача заблокирована, `php vendor/bin/todo-md set <ID> status=blocked` и указать причину в разделе "Риски и зависимости".

6. **Отмена**:
   - `php vendor/bin/todo-md cancel <ID>` — переводит в `cancelled`, переносит в `todo/cancelled/`. Ссылки обновляются автоматически.

> **CLI-команды** атомарно синхронизируют `status` ↔ папку ↔ ссылки и прогоняют валидатор. При ошибке изменения откатываются. Резервная копия — в `.todo-md-backup/`. Полный список: [STATUSES.md](../docs/todo-md/reference/STATUSES.md).

## Эпики

Эпик — это крупная единица работы, объединяющая набор связанных задач. Эпик хранится в папке `todo/`.

### Правила работы с эпиками:

- **Концепция:** Эпик должен содержать User Story или Job Story, объясняющую его ценность.
- **Простое описание:** Эпик должен объяснять проблему и ожидаемый результат человеческим языком до технических деталей.
- **Цель (SMART):** Эпик должен иметь одну конкретную, измеримую и ограниченную по времени техническую цель.
- **Требования (MoSCoW):** Требования в эпике приоритизируются по методу MoSCoW (Must, Should, Could, Won't).
- **План:** План реализации содержит последовательный список задач (TASK-ссылки).
- **Отслеживание прогресса:**
    - Прогресс фиксируется чекбоксами `[ ]` / `[x]` в плане реализации.
    - При завершении задачи (`done`) исполнитель обязан отметить её выполненной в плане соответствующего эпика.
    - Команда `todo-md done` автоматически обновляет путь ссылки в эпике (например: `[TASK-ID](done/TASK-ID.todo.md)`).
- **Актуализация:** Если в ходе работы меняется план, зависимости или scope — автор актуализирует текст плана и список задач в файле эпика.
- **Завершение:** Эпик считается выполненным, когда все `Must Have` требования закрыты, задачи выполнены, и пройдено Definition of Done (DoD).

## Версионирование задач

При изменении задачи или эпика:
- Обновлять дату `created` или поле в YAML front matter (если добавлено поле `updated`).
- Добавлять запись в раздел "История изменений" (для шаблонов, поддерживающих этот раздел); дата записи — в том же формате, что lifecycle-поля (`YYYY-MM-DD` либо `YYYY-MM-DD HH:MM:SS (unix_ts)`), см. [DATES.md](../docs/todo-md/reference/DATES.md).
- При значительных правках постановки сохранять предыдущие версии в комментариях, если это важно для контекста.

## Управление выполненными задачами (Папка done)

Выполненные задачи перемещаются в `todo/done/`.

1. **Проверка**: Статус `done`, критерии приёмки отмечены, результат заполнен.
2. **Действие**: `php vendor/bin/todo-md done <ID>` — атомарно переносит файл в `todo/done/` и обновляет ссылки.
3. **Архив**: Задачи хранятся в `done` бессрочно. Названия файлов не меняются.

## Управление бэклогом (Папка backlog)

Задачи на будущее или требующие уточнения хранятся в `todo/backlog/`.

1. **Назначение**:
   - Задачи, планируемые на будущее.
   - Идеи, требующие дополнительного анализа.
   - Задачи, не соответствующие Definition of Ready.
2. **Процесс**: `php vendor/bin/todo-md backlog <ID>` — переносит в `backlog/`. Когда задача готова — `php vendor/bin/todo-md set <ID> status=todo` возвращает её в активную папку.

## Управление отмененными задачами (Папка cancelled)

Если задача или эпик признаны неактуальными, они перемещаются в `todo/cancelled/`.

1. **Действие**: `php vendor/bin/todo-md cancel <ID>` — переводит в `cancelled`, переносит файл, обновляет ссылки.
2. **Ссылки**: Ссылки в плане эпика обновляются автоматически.
