# TASK-validate-duplicate-ids: Валидатор и ID-команды уведомляют о дубликатах ID задач

## 0. Простое описание (Human Brief)

### Проблема простыми словами (Problem)

Валидация в todo-md **по-файловая**: `validate` проверяет каждый файл сам по себе, а `Parser::buildIdIndex()` молча перезаписывает индекс — `$index[$id] = [...]` без проверки, что ID уже занят. Две копии одной задачи (одинаковый ID в разных файлах) проходят `todo-md validate` с exit 0, а ID-команды (`set`/`start`/`done`/`review`/…) молча правят только одну копию.

Живой кейс (репозиторий пакета, 2026-11-25, merge PR #58): в ветке реализации файл задачи был перенесён `todo/ → todo/done/`, а в `master` параллельно влит PR #57 с постановочной версией того же файла в `todo/`. Merge-base файл не содержал, поэтому git оставил **обе** копии: `todo/TASK-x.todo.md` (`status: todo`) и `todo/done/TASK-x.todo.md` (`status: done`, заполненный `pr`). `validate .` и CI на merge-коммите — зелёные; дубликат нашёлся только вручную при самопроверке.

Последствия тихого дубликата:

- валидация даёт ложный сигнал «всё чисто» — агент и владелец не знают о проблеме;
- `set TASK-ID priority=P1` меняет одну копию, вторая остаётся разъехавшейся (проверено на воспроизведении: изменился только файл в `todo/`, копия в `todo/done/` осталась со старым значением);
- противоречивое состояние (`status: todo` против `status: done` для одного ID) ломает семантику ID как уникального ключа доски.

### Варианты или путь решения (Solution Sketch)

Дубликаты ID — ошибка. Обнаружение — на уровне дерева (индекс ID всегда строится по всему дереву), уведомление — везде, где агент работает по ID:

```text
Error: duplicate task ID `TASK-x`:
  - todo/TASK-x.todo.md (status: todo)
  - todo/done/TASK-x.todo.md (status: done)
Resolve the duplication (keep one file) before running validate or ID commands.
```

Реализация: новый `Parser::findDuplicateIds(array $files): array<string, list<string>>` — группировка путей по ID файла; `cli_validate()` прогоняет её по `$idFiles` (всё дерево) и завершает с ошибкой; ID-команды (`findFileById` → все переходы и `set`) при неоднозначном ID отказывают с тем же сообщением. Вывод формулировать для агента: конкретные пути, что делать дальше (оставить один файл / указать явный путь).

### Ожидаемый результат (Expected Result)

Доска с двумя файлами одного ID: `todo-md validate` — ненулевой exit и сообщение со списком путей (какие файлы, какой у них status); `todo-md set/done/review TASK-ID` — отказ с тем же сообщением вместо молчаливой правки одной копии. Здоровая доска (ID уникальны) — поведение не меняется; fixture-тесты зелёные.

## 1. Концепция и Цель (Concept and Goal)

### История (User Story)

> Как AI-агент или владелец проекта, работающий с доской через CLI, я хочу получать явную ошибку при дубликате ID задачи — в `validate` и при любой ID-команде — чтобы не оперировать задачей, у которой существует противоречивая вторая копия.

### Цель по SMART (Goal)

В следующем минорном релизе: дубликат ID (два и более `.todo.md` с одинаковым именем файла в дереве `todo/`) — ошибка валидации с перечнем файлов и статусов; ID-команды при неоднозначности отказывают с тем же сообщением. Критерий: fixture-тесты (дубликат в validate, дубликат в ID-команде, здоровая доска без изменений) зелёные, `make check` проходит.

## 2. Контекст и Границы (Context and Scope)

*   **Где делаем:**
    *   `src/TodoMd/Parser.php` — `findDuplicateIds()`; `findFileById()` — сбор всех совпадений вместо первого попавшегося (или возврат ambiguity).
    *   `src/bootstrap.php` — `cli_validate()` (проверка по всему дереву ID-индекса, ошибка + exit 1 до валидации файлов); команды `set`, `start`, `review`, `done`, `cancel`, `backlog`, `history` — отказ при неоднозначном ID.
    *   `src/TodoMd/Validator.php` — при необходимости прокидка сообщения (индекс строится в `checkOnBoard` для post-write проверки переходов).
    *   `tests/` — fixture-тесты; `docs/` — при необходимости справочник валидации.
*   **Текущее поведение:** `buildIdIndex()` — последний файл затирает предыдущий; `findFileById()` возвращает первое совпадение; валидация файла изолирована от дерева.
*   **Прецеденты для переиспользования:** формат сообщений об ошибках CLI (`Error: ...` + exit 1); структура fixture-тестов `ValidateTest`.
*   **Критичные конвенции:** PHP 8.4, `declare(strict_types=1)`; читаемость важнее производительности; `make check` перед PR.
*   **Границы (Out of Scope):** автоматическое разрешение дубликатов (merge/выбор копии) — только обнаружение и уведомление; `export-jsonl` и `dashboard` (работают списком, не по ID); ключи конфига для «разрешить дубликаты»; изменение формата имени файла/ID.

## 7. Риски и зависимости (Risks and Dependencies)

- Риск 1: у потребителей-репозиториев с историческими дубликатами в архиве `validate` начнёт падать — это требуемый сигнал, но заметить в CHANGELOG релиза («несовместимость в 0.x», по регламенту отмечается явно).
- Риск 2: порядок обхода файлов нестабилен — сообщение должно сортировать пути детерминированно (например, `sort()`), чтобы тесты и вывод агента были воспроизводимыми.
- Риск 3: отказ ID-команд при дубликате может заблокировать агента в середине перехода — смягчается явной подсказкой про явный file-путь (Should).
- Зависимостей нет; целевая версия — следующий минорный релиз.
