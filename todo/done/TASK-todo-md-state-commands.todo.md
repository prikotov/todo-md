# TASK-todo-md-state-commands: Команды смены состояния задач (create/done/start/review/cancel/set)

## 0. Простое описание (Human Brief)
### Проблема простыми словами (Problem)
- Переход задачи между статусами требует вручную: править `status` в front matter, переносить файл в нужную папку, чинить относительные ссылки, запускать валидатор.
- Это много деталей «в голове» сразу — агенты и люди ошибаются (пример: перенос файла не в ту папку).

### Варианты или путь решения (Solution Sketch)
- CLI-команды, делающие переход атомарно: правят `status`, переносят файл, чинят ссылки, прогоняют валидатор, отказываются сохранять при ошибке.

### Ожидаемый результат (Expected Result)
- Смена состояния — одна команда; доска не рассинхронизируется.

## 1. Концепция и Цель (Concept and Goal)
### История (User Story)
> Как исполнитель (агент или человек), я хочу менять статус задачи одной командой, чтобы не держать в голове синхронизацию front matter, папки и ссылок.

### Цель по SMART (Goal)
Реализовать `todo-md-create`, `todo-md-done`/`start`/`review`/`cancel`/`backlog`, `todo-md-set`: каждая атомарно обновляет `status`, переносит файл в каноническую папку, чинит относительные Markdown-ссылки и прогоняет валидатор.

## 2. Контекст и Границы (Context and Scope)
*   **Где делаем:** новые `bin/todo-md-*`; общий парсер/индекс (как в валидаторе и export).
*   **Текущее поведение:** статус и папка синхронизируются вручную; валидатор ловит рассинхрон, но не чинит.
*   **Границы (Out of Scope):**
    *   Batch-операции над многими задачами.
    *   Undo/backup — второй шаг.

## 3. Требования, MoSCoW (Requirements)
### 🔴 Обязательно (Must Have)
- [ ] `create` — задача/эпик из шаблона, slug-ID, проверка коллизий, `created` = сегодня.
- [ ] `done`/`start`/`review`/`cancel`/`backlog` — атомарно: `status` + перенос в папку + правка ссылок.
- [ ] После записи — автопрогон валидатора; отказ при ошибке.
- [ ] Канонический путь (никогда не «не туда»).

### 🟡 Желательно (Should Have)
- [ ] `set <ID> <field>=<value>` для точечной правки метаданных.
- [ ] Undo/backup перед mutating-операцией.

### 🟢 Опционально (Could Have)
- [ ] `note <ID>` — дописать временную заметку.

### ⚫ Не будем делать (Won't Have)
- [ ] Параллельные захваты задач (claims) — отдельное направление.

## 4. План реализации (Implementation Plan)
1. [ ] Fixture-тесты для `init`/`validate` (enabler) — без них mutating-CLI не выпускать.
2. [ ] Общий модуль парсера/индекса (переиспользовать из валидатора).
3. [ ] `create` из шаблона.
4. [ ] `done`/`start`/`review`/`cancel`/`backlog` с правкой ссылок.
5. [ ] `set`.
6. [ ] Undo/backup.

## 5. Критерии приёмки (Definition of Done)
- [ ] Команды атомарно синхронизируют status↔folder↔links.
- [ ] После каждой записи валидатор проходит.
- [ ] Fixture-тесты покрывают переходы и правку ссылок.

## 9. Комментарии (Comments)
CLI выживает на стороне записи, потому что shell (`mv`+`sed`) не знает канонического пути и не чинит относительные ссылки. Доказательство — ошибочный перенос задачи в `done/` корня репо в сессии 2026-07-25.
